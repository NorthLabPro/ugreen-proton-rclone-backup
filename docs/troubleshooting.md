# Troubleshooting

This page documents problems encountered while setting up and running the UGREEN NAS → Proton Drive backup with rclone.

The solutions below are based on the actual setup used for this project.

> [!IMPORTANT]
> Before troubleshooting anything else, check your rclone version:
>
> ```bash
> rclone version
> ```
>
> This setup was successfully tested with **rclone 1.74.4**.

---

## 1. Proton Drive authentication stops working

### Symptom

The Proton Drive connection worked during configuration, but later commands such as:

```bash
rclone lsd protondrive:
```

fail with an authentication error.

### Possible cause

A temporary six-digit Proton 2FA code may have been saved in `rclone.conf`.

The six-digit code expires, so it should not remain as a permanent authentication value.

### Check the configuration

Run:

```bash
rclone config show
```

Look for:

```text
2fa =
```

If an old `2fa =` entry exists, remove it:

```bash
sed -i '/^2fa =/d' /config/rclone/rclone.conf
```

Then test again:

```bash
rclone lsd protondrive:
```

> [!CAUTION]
> Do not post the complete contents of `rclone.conf` online. It contains authentication information.

## 2. Confusion about `otp_secret_key`

During `rclone config`, rclone may show:

```text
Option otp_secret_key
```

and later:

```text
Enter the password:
```

This is easy to misunderstand.

At this point, rclone is **not asking for your normal Proton password**.

It is asking for the **Base32 OTP Secret Key** used to generate your Proton 2FA codes.

The OTP Secret Key is also **not** the temporary six-digit code shown by your authenticator.

### The three different values

| Value | What it is |
|---|---|
| Proton password | Your normal Proton account password |
| 6-digit 2FA code | Temporary code generated by your authenticator |
| OTP Secret Key | Long Base32 secret used to generate 2FA codes |

Never publish any of these values.

## 3. Files upload but cannot be opened in Proton Drive

### Symptom

rclone reports that the upload completed, and the files appear in Proton Drive, but uploaded images cannot be opened correctly.

### What happened during testing

This problem occurred while testing a newer rclone version.

Returning to:

```text
rclone 1.74.4
```

resolved the issue in the setup documented here.

### Check your version

```bash
rclone version
```

The Docker Compose file supplied with this repository deliberately uses:

```yaml
image: rclone/rclone:1.74.4
```

instead of:

```yaml
image: rclone/rclone:latest
```

This prevents Docker from silently moving the installation to a newer version.

> [!IMPORTANT]
> This does not mean every newer rclone version is broken.
>
> It means **1.74.4 is the version verified with this particular setup**. Test newer versions before using them for a large archive.

## 4. Error 422 during upload

### Symptom

The log may contain an HTTP/API error involving:

```text
422
```

### What to do

Do not immediately restart the entire backup from scratch.

The backup command used in this project includes:

```text
--retries=20
--low-level-retries=50
--retries-sleep=30s
```

This gives temporary Proton/API failures time to recover.

If the transfer eventually stops, run the same `rclone copy` command again.

Already transferred files do not normally need to be uploaded again.

---

## 5. `already exists`

### Symptom

An upload fails because Proton Drive reports that an item already exists.

This can happen after an interrupted or incomplete upload.

The backup command used by this project includes:

```text
--protondrive-replace-existing-draft=true
```

This helps rclone deal with an existing incomplete/draft upload.

If the problem persists, inspect the affected file in Proton Drive before deleting or replacing anything.

---

## 6. `not found`

### Symptom

rclone reports that an expected Proton Drive object cannot be found.

This may occur after interrupted operations or while Proton Drive and rclone are resolving the state of an upload.

### First response

Allow the configured retries to run.

If the backup stops completely, run the same `rclone copy` command again.

Do not immediately delete the destination or restart a large backup from zero.

## 7. Power failure or lost internet connection

This is especially important for large backups.

If the NAS loses power, Docker stops, or the internet connection disappears, the entire backup does **not** need to be restarted manually from the beginning.

After the NAS and container are running again, execute the same command:

```bash
rclone copy "/data/photo" protondrive:"YOUR DESTINATION" \
  --progress \
  --transfers=1 \
  --checkers=2 \
  --create-empty-src-dirs \
  --retries=20 \
  --low-level-retries=50 \
  --retries-sleep=30s \
  --protondrive-replace-existing-draft=true \
  --log-file=/config/photo-backup.log \
  --log-level=INFO
```

rclone compares the source and destination and continues with the files that still require transfer.

## 8. rclone cannot see the NAS files

### Symptom

Inside the Docker container:

```bash
ls /data/photo
```

shows nothing, or the directory does not contain the expected files.

### Check the Docker volume

Your `docker-compose.yml` contains something similar to:

```yaml
- "/path/to/your/photos:/data/photo:ro"
```

The path on the **left** must point to the actual folder on the UGREEN NAS.

Example:

```yaml
- "/volume1/Photos:/data/photo:ro"
```

Restart/recreate the Docker project after changing the volume mapping.

Then test:

```bash
ls /data/photo
```

You should now see the NAS folders/files from inside the container.

---

## 9. Proton Drive folders are not listed

Test:

```bash
rclone lsd protondrive:
```

If this fails:

1. Check that the remote is actually called `protondrive`.
2. Check the rclone version.
3. Check the Proton login configuration.
4. Check that the OTP Secret Key was configured.
5. Check for an expired `2fa =` entry.

You can list configured remotes with:

```bash
rclone listremotes
```

Expected result:

```text
protondrive:
```

## 10. Test one file before troubleshooting thousands

Before running a large backup, always test one file:

```bash
rclone copy "/data/photo/example.jpg" protondrive:"Test74"
```

Then verify the file directly in Proton Drive.

Check that it:

- appears in Proton Drive
- opens correctly
- downloads correctly
- is not corrupted

This simple test can prevent discovering a configuration or compatibility problem after hundreds of gigabytes have already been transferred.

## 11. Check the backup log

The full backup command stores a log here:

```text
/config/photo-backup.log
```

View the latest entries:

```bash
tail -n 50 /config/photo-backup.log
```

Follow the log live:

```bash
tail -f /config/photo-backup.log
```

Search for errors:

```bash
grep -i "error" /config/photo-backup.log
```

The log is usually the first place to look when a transfer stops unexpectedly.

---

## 12. Do not switch to `sync` to fix problems

The backup in this project deliberately uses:

```bash
rclone copy
```

Do not change it to:

```bash
rclone sync
```

simply because a transfer has problems.

`sync` has different behavior and can delete files at the destination to make it match the source.

For an important family archive, understand the consequences before using `sync`.

## Still having problems?

Start with these three commands:

```bash
rclone version
rclone listremotes
rclone lsd protondrive:
```

Then check:

```bash
tail -n 50 /config/photo-backup.log
```

These usually provide enough information to identify where the problem occurs.
